# ADR-0005 카탈로그 편집은 앱 안 관리자 화면

- 상태: 제안
- 날짜: 2026-11-03

| 항목 | 내용 |
|---|---|
| 맥락 | 카탈로그(SSR·ArtCraft·가이드·7일 계획·탐색기 예시 등)는 DB 시드로 옮긴다(ADR-0003). 출시 후 문구·앱 정보·이미지를 누가 어떻게 고칠지 정해야 한다(Q3 → D21). |
| 선택 | 같은 Next.js 앱에 `/admin` 라우트 그룹: AD1 카탈로그 목록(테이블 선택·검색)·AD2 항목 편집 폼·AD3 이미지 업로드(Storage)·AD4 변경 이력·AD5 번들 코드. 권한은 관리자 테이블 + RLS(사용자 세션으로 쓰고 DB가 판정, service_role 미사용), 모든 변경은 같은 트랜잭션에서 감사 기록. **MVP-2·축소 범위**(D39): 편집 대상은 `art_apps`·`prompts`·`guide_pages` 문구 + 이미지(AD3) + 이력(AD4) + 코드(AD5)로 한정, 나머지 카탈로그는 마이그레이션으로 고친다. 정본은 운영 DB(ADR-0003). 흐름은 02 flow-5, 엔드포인트·테이블은 `04_API.md` AD절·`05_DATA_MODEL.md` 참조. |
| 대안 | ① 저장소 시드만(SQL 수정 → 마이그레이션 배포): 추가 화면이 없지만 문구 하나에도 개발자·배포가 필요하고 변경 이력이 커밋에만 남는다. ② 외부 CMS(Sanity·Strapi 등): 편집 UI는 좋지만 저장소가 둘로 갈라져 사용자 데이터와 노드 id 참조 무결성이 깨지고, 새 의존성·비용·키 관리가 늘어난다. |
| 결과 | 얻음: 배포 없이 내용 수정, DB가 권한을 강제(화면 우회 불가), 감사 기록으로 추적·복구. 잃음: 화면 5개 구현·테스트(3테이블로 줄여 부담 완화, D39), 관리자 권한·감사 RLS가 높음 위험(보안 리뷰 필요), 시드와 운영 DB 차이 관리. 되돌리기: 화면을 내리면 ①로 복귀 — 데이터는 그대로라 낮은 비용. |
